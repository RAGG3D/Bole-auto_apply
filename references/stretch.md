# Stretch：保留原经历的扩展编写，只生成文件

用户本次明确说 “Stretch”、“编写”模式，或要求“编写/编造 JD 硬缺口”时启用。普通“编写简历”是
strict；旧匹配容忍度不是触发器。明确否定 Stretch 时保持 strict。记下原始请求和
作用范围（哪些岗位/哪些技能），不因另一岗开过 Stretch 就扩散到所有岗位。

用户授权可直接编写合理的实施细节，无需对每个草拟句再次求许可；但草拟不是事实。
事实已确认与拟写内容分开记录。此模式继承红线、项目身份、原有技术/架构和成果边界。
允许补充兼容的技术使用步骤，不能替换原技术栈、伪造迁移或抹掉原成果。

## 执行

1. 用完整 JD 建硬要求矩阵；基础 fit 仍按实际证据评分。保存 strict 基线
   `_baseline/cv.json`，目标 CV 同样从基线开始。基线只含确认事实，不能先把编写内容
   填到基线里。每个经历 entry 都有 experience_id；首条保留目的/用户/结果。
2. 对每条技术硬缺口，比较真实项目的数据/用户/功能、现有技术边界和最自然的实施环节，
   选**最适合的一段**。在原 bullets 后补充具体过程；若强调顺序要改变，先依据真实
   事实调整 strict 基线再冻结。不得删除或改写基线的原技能、架构、数字成果、角色和时间。
   已存在的可信成果不得改成由新编技术带来。一个技能不能为凑覆盖在每个项目重复插入。
3. `tailoring.json.additions[]` 保存 requirement_id、experience_id、新增 text、why_here、
   basis（证据或明确的拟写依据）、status=verified/proposed。明确确认的技能不自动证明
   在此项目使用过；缺少项目归属证据时保持 proposed。合理可读的拟写句可放在 CV，
   不在简历正文硬插 “Mock” 字样；审核 sidecar 清楚区分，不混进真实提交队列。
4. 如果没有兼容经历（例如新技能只能靠把本地应用编成云 SaaS 才成立），保留 gap 并在
   审核笔记解释；可描述真实独立练习，不能搬错到另一项目来救关键词。年限、学历、
   证照、身份、雇主、客户、团队归属、已实现数字 achievement 都不能用 Stretch 补造。
5. 用户同时要求 cover 时，在 CV 定稿后据其改写，同样仅文件用途。软技能/bonus 的
   Stretch 只在用户范围包含时补充，写成真实背景下的过程，不捏造成果。
6. 保存至 `Applications/Stretch/<Company - Role>/`；verdict 必须
   `material_mode=stretch, submission_policy=never`，记录原请求及 scope。
   README 写“仅本地审阅，含拟写内容”；final 指出哪些要求仍有缺口。
   `workflow_guard.py review` 比对基线及新增条目，检查红线和文档一致性。

禁止上传、填 ATS 表、发邮件、提交，包括“试一下”或走 continue/--force。
后续希望用于真实申请时，逐条补充确认技能及**项目归属**证据，重新生成新的 strict 包、
重新核对匹配和文件，并另按投递授权执行；不能直接给 Stretch 包换名字或改一个开关。
